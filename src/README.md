# `src/` — the site sources

Everything under `src/` is hand-edited. Everything in `dist/` is generated by
[`build.mjs`](../build.mjs) and is gitignored — **never edit `dist/`**.

```bash
node build.mjs            # build into dist/
node build.mjs --watch    # rebuild on every change under src/ or assets/
node build.mjs --check    # verify EN/ES parity, write nothing
```

The build is plain Node with no dependencies — there is nothing to `npm install`.

## Layout

```
src/
  site.config.json   nav, footer, social links, scripts, per-page metadata
  layouts/base.html  the one page shell every page is rendered into
  partials/          header, nav, footer, scripts, head metadata, favicon links
  pages/*.html       EN page bodies (plus 404.html, EN only)
  pages/es/*.html    ES page bodies
  standalone/        copied verbatim to the site root: the infography page and favicon.ico
```

`assets/` and `images/` stay at the repo root and are copied into `dist/` as-is.
The build also **generates `dist/robots.txt` and `dist/sitemap.xml`** from the
config — there are no hand-written copies to keep in step.

## The point of all this

Header, nav, footer and the script list used to be copy-pasted into ~20 files.
They now exist once. Concretely:

| To change | Edit | Pages updated |
|---|---|---|
| A nav link, its label or its order | `site.config.json` → `nav` | all 18 |
| Footer text, social links | `site.config.json` → `strings` / `socialLinks` | all 18 |
| A JS or CSS file loaded by every page | `site.config.json` → `scripts` / `stylesheets` | all 18 |
| A page's `<title>` or search/preview description | `site.config.json` → `pages` | that page, its sitemap entry |
| The canonical domain | `site.config.json` → `siteUrl` | canonical, hreflang, og:url, sitemap on all 18 |
| Header/nav/footer *markup* | `partials/*.html` | all 18 |
| The `<head>` or page shell | `layouts/base.html` | all 18 |
| The prose on one page | `pages/<name>.html` (+ `pages/es/<name>.html`) | that page |

## Adding a page

1. Write `src/pages/mypage.html` — just the `<section id="main">` block, no
   header/nav/footer.
2. Write the Spanish twin at `src/pages/es/mypage.html`.
3. Add it to `pages` in `site.config.json`:

   ```json
   "mypage": {
     "bodyClass": "",
     "title": { "en": "My page — SyMptOMS", "es": "Mi página — SyMptOMS" },
     "description": {
       "en": "One sentence, under ~160 characters, saying only what the page says.",
       "es": "Una frase, de menos de ~160 caracteres, que diga solo lo que dice la página."
     }
   }
   ```

   The title is what the browser tab and search results show — make it
   distinct. The description is the search snippet and the link preview, and
   `--check` **requires** it on every indexable page. The page gets canonical,
   `hreflang`, Open Graph tags and a sitemap entry automatically.

4. To put it in the nav, add one entry to `nav`:

   ```json
   { "page": "mypage", "label": { "en": "My Page", "es": "Mi página" } }
   ```

   The page highlights its own nav entry automatically. A page that should not
   highlight anything (like `rct`) sets `"nav": null`.

5. `node build.mjs`.

`--check` fails the build if a page is missing its EN or ES twin, is missing a
title or description in either language, or exists in `pages/` without an entry
in the config. `firebase deploy` runs the build first, so a deploy aborts on any
of these.

### Less common page options

| Option | Effect | Used by |
|---|---|---|
| `"nav": null` | highlight no nav entry | `rct`, `404` |
| `"scripts": [...]` | JS for this page only, content-hashed | `blog`, `publications` |
| `"locales": ["en"]` | build in these locales only; the language switcher sends the others to their homepage | `404` |
| `"noindex": true` | `<meta name="robots" content="noindex">`, no canonical/hreflang, left out of the sitemap | `404` |
| `"rootRelative": true` | `{{prefix}}` becomes `/` and nav/logo links become root-absolute | `404` |
| `"bodyClass": "wide-measure"` | paragraphs cap at 100ch instead of 68ch | `index`, `publications`, `blog`, `privacy-policies`, `rct` |
| `"bodyClass": "page-rct"` | centres the article's title and paragraphs, like the home intro | `rct` |
| `"bodyClass": "page-about"` | wider container and two-per-row team cards at 981-1280px | `about` |

`rootRelative` exists for exactly one case: **Firebase Hosting serves
`404.html` for any missing path at any depth**, so on `/es/a/b/missing.html` a
relative `assets/css/main.css` would resolve to `/es/a/b/assets/…` and the page
would render unstyled. Any page body that links somewhere should still use
`{{prefix}}` — it is what makes that work.

**If `node build.mjs --watch` is running when `build.mjs` itself changes, restart
it.** It watches `src/` and `assets/` (not `images/`), and recomputes the
`?v=` cache-busting hashes on every rebuild -- before 2026-09-14 it kept the
hashes from its first build, so a CSS change could keep showing old styles. The watcher re-reads the config, layout and partials on every change, but
its own code stays whatever it was when it started — it will keep writing
`dist/` with the old build logic and no warning.

## Page source blocks

A page source is normally just its `<section id="main">` block. Three optional
named blocks cover the things that live outside it:

```html
<!-- @head -->
<script> /* goes into <head> */ </script>
<!-- /@head -->

<!-- @prelude -->
<!-- markup placed inside #masthead, after the nav, e.g. the home page CTA
     banner, which hangs just below the green rule on desktop -->
<!-- /@prelude -->

<section id="main"> ... the page ... </section>

<!-- @scripts -->
<script> /* runs after the shared script list, e.g. the initBlog(…) call */ </script>
<!-- /@scripts -->
```

## Giving one page its own JavaScript

Put the file in `assets/js/`, then list it in that page's `pages` entry in
`site.config.json`:

```json
"blog": {
  "scripts": ["assets/js/sanitize-html.js", "assets/js/blog.js"],
  "title": { "en": "…", "es": "…" }
}
```

Order is preserved and the list is appended after the site-wide `scripts`, so
the page's own files load last and can depend on each other. They are
content-hashed exactly like the shared ones, and `node build.mjs --check` fails
if one does not exist on disk.

**Rendering for `blog` and `publications` lives in those files, not in the page
sources.** Each page source carries markup plus one `initBlog(…)` /
`initPublications(…)` call whose strings come from `site.config.json` — so the
same init block works in both locales. Do not put rendering back inline: it was
duplicated per language for years and the copies drifted (the Spanish blog was
rendering two English strings).

Two things those files build that the page sources do not contain:

- **The publications filter `<select>`.** The page source has only the five
  `.btn` chips; `publications.js` derives a `<select>` from them for screens
  736px and narrower, where main.css makes every `<button>` full width and the
  chips stack five rows deep. Add a filter by adding a chip — never write the
  `<option>`s by hand, or the two controls will disagree between locales.
- **The blog's whole page furniture.** `blog.js` sorts posts newest first,
  drops duplicate ids, builds the index cards and their pager in
  `#post-pager` (three cards a page), the sticky post rail in `#post-rail`,
  each article's meta row (date, reading time, tags, source), its outline when
  the post has two or more headings, and the `#post-<id>` history handling.
  The page source is four empty containers, one `<hr class="blog-split">` and
  the `initBlog(…)` call.

## Template syntax

A deliberately small subset — see the top half of `build.mjs`:

| Syntax | Meaning |
|---|---|
| `{{ name }}` | insert a value; dotted paths (`strings.taglineTop`) work |
| `{{> partial }}` | insert `partials/partial.html` |
| `{{#if x}}…{{else}}…{{/if}}` | conditional |
| `{{#each xs}}…{{/each}}` | loop; fields of the item are in scope |

Values are inserted as raw HTML — the footer text and social labels are
authored here, not user input. The one exception is page **titles and
descriptions**, which the build escapes before inserting: they end up inside
`content="…"` attributes, where a stray quote would silently cut the tag short. A tag alone on its line contributes no blank
line, and a multi-line value inserted on its own line keeps the surrounding
indentation.

## Locale paths

`{{prefix}}` is `` for EN pages, `../` for ES pages and `/` on a `rootRelative`
page (the 404). Use it for anything under `assets/` or `images/`, and for links
to other pages from inside a body. Nav links between pages of the same language are
bare filenames; the build works out the language-switcher hrefs itself.

## Notes

- `src/legacy/` **was deleted on 2026-09-10**. It held
  `symptoms-platform.html`, the two unmodified HTML5 UP sidebar demos and the
  `es/*_OLD.html` pages. Recover them from git at their *pre-refactor* paths
  (`git show HEAD:symptoms-platform.html`), not under `src/legacy/`.
- **A card that links somewhere is one link.** Mark the card
  `<section class="box feature has-link">` and its title link
  `<a class="card-link" href="…">`; the title is stretched over the whole card,
  and hover/press feedback comes with it. Do not wrap the image in a link. Cards
  that go nowhere just omit both classes. See `use-cases.html` or `tools.html`.
- **Block order can change with the viewport, and it lives in CSS.**
  `tools.html` puts each group title with its own cards below 981px (one
  `.row.tool-grid`, classes `tool-title-*` / `tool-card-*`, custom.css section
  18). `blog.html` hides its rail column (`blog-side`) below 981px, where the
  card grid above the article already does that job. If you reorder or
  reclass anything in those two, check the page at 390px as well as on a
  desktop. **Do not use the template's `imp-medium` on either** — it is
  `order: -1` below 980px and will jump a column over everything above it.
- **The blog rail is sticky, and the sticky is on the wrapper.** `#post-rail`
  in the page source is the sticky box; the `<nav>` inside it is built by JS
  and would have only its own height to travel in. Keep the wrapper, and keep
  its column stretched — no `align-self` on `blog-side`.
- **A bare `<button>` gets the site's big green button styling**, including
  `width: 100%` at 736px and below, because main.css's button rule matches the
  element and not just `.button`. Anything that is a control but not a call to
  action — the publications filter chips, the blog pager — has to undo that at
  id strength: section 0 restates the fill on `button:hover` and
  `button:active`, which beat a plain class.
- **Buttons: use `.button` and nothing else.** Every button on the site is white
  on `--button` (`#3cb486`) with no border, in every state -- a deliberate
  choice that fails WCAG AA at 2.60:1. Do not add inline colours to a button, and do not
  give one a hover colour; hover and press feedback come from custom.css
  section 16.
- **The language switcher carries a globe**, drawn as a `::before` on
  `ul.menu-lang` (custom.css section 1) so that the two copies `main.js` makes
  — the mobile title bar and the foot of the panel — get it for free. Do not
  add an element for it, and do not drop its `font-weight: 900`: `fa-globe`
  lives only in Font Awesome's Solid face and renders nothing without it.
- **The header tagline is two strings**, `taglineTop` and `taglineBottom`, one
  per line, inside the same home link as the logo. **Keep nav labels short.**
  Changing a label, either tagline string or the logo changes the width the
  masthead needs on one row. Re-measure the two-row fallback thresholds in
  custom.css section 5 (999px EN, 1139px ES today), or a longer label will
  quietly push EN/ES off the right edge between 981px and the threshold.
- **Hover styles must work on phones too**: put them inside
  `@media (hover: hover) and (pointer: fine)`, give each one an `:active`
  counterpart, and keep any movement inside
  `@media (prefers-reduced-motion: no-preference)`. custom.css section 16 is the
  pattern.
- **A `socialLinks` entry needs `style` as well as `icon`** — `brands` for a
  company mark, `solid` for a generic Font Awesome glyph. Get it wrong and the
  icon renders as nothing, silently. `label` is the accessible name; it is
  hidden visually, so it is all a screen reader gets.
- **Fetching from the Realtime Database? Request a specific node.** Root reads
  are denied — `/geotecblog`, `/publications` and `/lastUpdated` are the public
  ones, and RTDB refuses a path it cannot serve in full rather than filtering it.
- `assets/css/main.css` is the source of truth for the template's CSS; there
  is no SASS any more. Project styling goes in `custom.css`. The build does not
  touch CSS, but it does mirror `assets/` and `images/` into `dist/`, so a
  deleted file stops deploying.
- **Every asset path in a page body uses `{{prefix}}`**, inline `url(…)`
  included: `src="{{prefix}}images/foo.png"`. Never `images/` or `../images/`.
- **A new team member on About** is an
  `<img class="team-photo" src="{{prefix}}images/…" alt="Photo of …" width="…" height="…" loading="lazy" decoding="async" />`
  above the `<h3>` with their name (`Foto de …` in Spanish). Read `width` and
  `height` from the file: they stop the page jumping as the photo loads. The
  crop is set in CSS, so any photo shape works.
